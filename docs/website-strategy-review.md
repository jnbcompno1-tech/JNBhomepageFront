2026-10-08 후속 결정: 사용자는 현재 단계를 가능성 검토로 정리하고, 테스트용으로 먼저 배포한 뒤 수정하는 방식으로 요구사항 작성을 요청했다. 아래 보완 의견은 테스트 제작의 선행 차단 조건으로 두지 않고, 검토용 표시·대체 콘텐츠·테스트 이후 보완으로 처리한다. 현재 단계와 검수 기준은 [요구사항서](website-requirements.md)를 따른다. 아래 팀 검토 결과는 당시 판단 기록으로 보존한다.

## 판단 근거

회사 업무와 경험을 보여주고 이메일 문의로 연결한다는 목표에 비해 초기 기능 범위가 적절하다. 관리자·결제·문의 백엔드를 제외하고, 정적 콘텐츠와 이메일로 시작하는 방향을 유지한다. 대표자 경력과 회사 실적을 구분하고, 미확인 자료나 가상 실적을 공개하지 않는 원칙도 타당하다.

핵심 약점은 기술 구현 가능성이 아니라 콘텐츠와 운영 가정의 미확정이다. ‘디자인부터 양산까지’라는 포괄적 소개가 현재 JNB의 주력 업무와 맞는지, 공개할 사례가 있는지, 누가 정보를 고치고 문의에 답할지는 아직 확인되지 않았다. 원문 141줄의 통과 기준에는 미확인 항목의 처리 방안도 필요하므로, 아래 조건과 해결 시점을 함께 관리해야 한다.

사업 비중은 자료가 많은 순서만으로 정하지 않는다. 현재 원하는 고객과 수행 가능한 업무를 먼저 정하고, 확보한 근거로 그 설명을 뒷받침한다. 포트폴리오 3~6건은 조사 목표로 유지하며 통과의 필수 수량으로 만들지 않는다. 익명 사례도 주체·설명·이미지의 공개 가능성을 확인해야 한다.

## 유지할 선택과 보류할 선택

- **유지:** 정적 회사 소개, 이메일 주소 병기와 메일 작성 링크, 모바일·접근성 고려, 실제 자료 우선, 대표자와 회사 실적 구분, 단계별 검토.
- **잠정 유지:** Next.js App Router·TypeScript·CSS Modules·Vercel. 익숙한 참고 코드의 일부를 재사용할 수 있다는 근거는 있으나, 필수 기술이나 최저비용이라는 증거는 없다. 새 프레임워크 비교를 넓히기보다 운영 담당·예산·자산 조건을 먼저 확인한다.
- **기본 후보:** Vercel의 일반 Next.js 배포에서 본문을 정적 생성하고 필요한 이미지 최적화를 사용하는 방식. 순수 정적 파일 배포가 필요하거나 호스팅 비용 전제가 맞지 않으면 `output: 'export'`와 이미지 사전 변환을 비교한다. 이번 검토로 배포 방식을 확정하지 않는다.
- **보류:** 5개 독립 페이지의 확정, 사례 상세 페이지, 첫 화면 영상. 콘텐츠 양이 적으면 페이지를 합치고, 검토용 홈의 핵심 소개·업무·문의 흐름부터 확인한다. 영상은 실제 자산·모바일 성능·전송 비용을 확인한 뒤 선택한다.
- **현재 추가하지 않음:** CMS·문의폼·문의 저장 백엔드. 비개발자의 반복적인 즉시 수정, 문의 누락·담당 배정, 고객의 사이트 내 접수 요구 등 실제 필요가 확인되면 재검토한다.

## 확인한 기술·운영 사실

확인일 기준 Vercel Hobby는 개인·비상업용으로 제한된다. 따라서 회사 사이트의 무료 Hobby 사용을 전제하지 않은 전략은 타당하다. [Vercel Hobby 공식 문서](https://vercel.com/docs/plans/hobby)

Pro는 기본 월 US$20에 배포 가능한 좌석 1개와 월 US$20 사용 크레딧을 포함한다. 추가 좌석·사용량·유료 기능·세금은 별도이며 실제 계정의 총비용은 미확인이다. 예산 검토에는 도메인 갱신·메일·유지보수도 포함해야 한다. [Vercel Pro 공식 문서](https://vercel.com/docs/plans/pro-plan)

Next.js의 정적 생성과 `output: 'export'`는 구분해야 한다. 정적 내보내기에서는 기본 이미지 최적화와 일부 서버 기능을 사용할 수 없으므로, 정적 사이트라는 이유만으로 내보내기를 강제할 근거는 없다. [Next.js 공식 문서](https://nextjs.org/docs/app/guides/static-exports)

GSPLPLUS의 공용 프로젝트 데이터·포트폴리오·메타데이터 구조는 재사용 참고가 된다. 기존 문의 페이지의 이메일 표시와 회신 약속을 복사하는 것만으로 JNB의 문의 요구사항을 만족한다고 볼 수 없다. 기존 그래프는 GSPLPLUS 참고 프로젝트의 그래프이며 JNB 구현·실적의 증거가 아니다. 세부 확인은 [팀장 근거 기록](../.team-review/run_26485e569eeb/evidence.md)에 남겼다.

## 다음 행동과 재검토 조건

1. 대표님 확인용으로 현재 주력 문의 1~2개, 세 사업별 수행 범위, 첫 사례 후보 한 건, 이메일·수정·비용 담당을 묶어 확인한다. 모든 폴더 조사를 끝내는 것을 이 확인의 선행조건으로 만들지 않는다.
2. 확인 결과에 따라 포트폴리오 중심 또는 업무·진행 방식 중심 구성을 선택한다. 미확인 부분은 검토용으로 표시하고, 사실 주장으로 공개하지 않는다.
3. 위 보완 조건의 담당과 시점이 정리되면 전략 통과 여부를 확인하고 요구사항 정의 단계로 넘긴다. 실제 연락처·자료 권한·기능·성능·계정 검수는 해당 후속 단계에서 수행한다.

현재 업무가 소싱·공급에 집중되어 있으면 첫 소개의 강조 순서를 바꾼다. 공개 사례가 없으면 포트폴리오 중심 구성의 비중을 다시 판단한다. 수정·회신 담당을 확보할 수 없거나 운영비가 수용되지 않으면 운영·호스팅 방식을 재검토한다. 이는 회사 홈페이지 자체의 필요성을 부정하는 조건은 아니다.

원문 전략은 수정하지 않았다. 검토 보고서와 근거 기록만 추가했으며 요구사항서·구현·설치·배포·커밋은 수행하지 않았다. 회사 하위 자료 전체·실적·공개 권한·실제 수신함·고객 반응은 미확인으로 남는다.
