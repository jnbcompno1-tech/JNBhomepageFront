# 가독성 개선 계획

작성·검토 반영일: 2026-10-12. 대상: 전체 5개 페이지(홈·회사소개·사업영역·포트폴리오·문의).
참고 운영 주소: https://jnb-company.vercel.app. 구현과 검증은 현재 체크아웃의 로컬 사이트에서 진행한다.

## 1. 목표와 이번 구현 범위

양산 부품을 찾는 고객이 사업영역·공급 실적·문의 방법을 쉽게 읽도록 글자 크기, 대비, 줄 길이와 반응형 배치를 개선한다. 기존 페이지 구성, 사업 내용, 공급 실적, 이미지, 연락처·오시는 길, 검색 노출 설정은 유지한다.

이번에는 기존 시스템 글꼴로 CSS 중심의 개선을 완료한다. 글꼴 도입과 안내 문구 삭제·접기는 후속 결정으로 분리한다. 본문은 데스크톱과 모바일 모두 기본 16px로 진행하며, 구현 전에 별도 결정을 기다릴 필요는 없다. 새 패키지나 테스트 프레임워크를 추가하지 않는다.

## 2. 현재 상태와 근거

`src/components/Site.module.css` 검토 결과다. CSS 선언과 실제 렌더링 결과를 구분한다. 기존 조사에서 나온 '13px 이하 31개'는 첫 미디어 쿼리 앞의 `font-size` 선언 수이며, 뒤에 추가된 포트폴리오·오시는 길 스타일과 반응형 덮어쓰기를 포함한 요소 수가 아니다. 구현 시작 시 최신 코드의 계산된 스타일로 확인한다.

| 항목 | 관찰 | 개선 방향 |
| --- | --- | --- |
| 본문·목록 | 14~15px 본문과 더 작은 사업영역·포트폴리오 항목 | 읽어야 하는 본문·목록을 기본 16px로 통일 |
| 영문 소제목 | 일부 카드·모바일에서 8~11px | 짧은 라벨도 기본 12px 이상 |
| 푸터·안내 | 작은 글씨와 낮은 대비가 함께 나타남 | 내용 역할에 맞게 크기와 대비를 함께 보정 |
| 글자 크기 종류 | 장식용 큰 글자와 본문 크기가 혼재 | 전체 크기 개수 대신 본문·보조·제목 역할을 정리 |
| 반응형 배치 | 중간 폭에서 여러 열과 상세 목록이 좁아질 수 있음 | 글자를 키우면서 열 수·줄바꿈도 함께 확인 |
| 글꼴·안내 문구 | 운영체제별 글꼴 차이와 반복 안내가 있음 | 이번에는 유지하고 별도 후속 검토 |

다음은 불투명한 단색 조합의 대비 계산이다. 같은 회색도 배경에 따라 통과 여부가 달라진다.

| 글자색 | 배경색 | 대비(표시용 반올림) | 일반 글자 4.5:1 기준 |
| --- | --- | --- | --- |
| `#637185` | `#ffffff` | 4.96:1 | 통과 |
| `#69778b` | `#ffffff` | 4.55:1 | 통과 |
| `#69778b` | `#f2f5fa` | 4.17:1 | 미달 |
| `#6c7889` | `#ffffff` | 4.48:1 | 미달 |
| `#768397` | `#ffffff` | 3.84:1 | 미달 |
| `#5b687a`(보조색 후보) | `#f2f5fa` | 5.19:1 | 통과 |

줄 간격 1.7~1.9, `word-break: keep-all`, 섹션 여백, 제목 위계는 살린다. 다만 긴 영문·주소·확대된 글자가 넘치는 위치에는 필요한 줄바꿈 처리를 보완한다.

## 3. 적용 규칙

### 글자 크기

`globals.css`의 `:root`에 공용 변수를 두고 기존 선택자에서 재사용한다. 루트 기본 글꼴 크기는 브라우저 사용자 설정을 존중한다. 아래 px 값은 기본 16px 환경에서의 환산값이다.

| 역할 | 기본 크기 | 적용 예 |
| --- | --- | --- |
| 짧은 라벨 | `0.75rem`(12px) | 영문 소제목·배지 |
| 보조 설명 | `0.875rem`(14px) | 출처·상태 안내·저작권 |
| 본문 | `1rem`(16px) | 소개 문단·사업영역 목록·공급 실적·주소·문의 안내·내비게이션·버튼 |
| 강조 본문 | `1.125rem`(18px) | 도입 문단 등 필요한 곳 |
| 제목 | `1.5rem` / `2.125rem` / `3rem`(24 / 34 / 48px) | 카드·섹션·페이지 제목 |

모바일에서도 본문과 목록을 16px 아래로 줄이지 않는다. 긴 안내나 업무 조건은 중요도에 따라 본문 크기를 적용한다. 제목만 화면 폭에 맞춰 조절한다. 로고·장식 숫자까지 강제로 7개 크기에 맞추지는 않는다. CSS 검색뿐 아니라 미디어 쿼리가 적용된 최종 크기를 확인한다.

### 색상과 대비

- 회색은 본문 `#3d4b5e`, 보조 `#5b687a`를 우선 사용한다. 기존 브랜드색과 제목색은 역할이 분명하고 대비를 충족하면 유지한다.
- 이번 프로젝트의 읽는 텍스트 목표는 크기와 관계없이 4.5:1 이상이다. 실제 글자색·배경색·투명도 조합으로 계산하고, 통과 판정에는 반올림 전 값을 사용한다.
- 밝은 장식색 `#8a97a8`은 텍스트에 사용하지 않는다. 의미 있는 아이콘이나 입력 테두리에 사용한다면 해당 비텍스트 대비 기준도 별도로 확인한다.
- 흰색·옅은 회색 카드·색상 배경과 버튼의 기본·hover·focus 상태를 확인한다. 이미지나 그라데이션 위의 글자는 글자가 놓이는 배경에서 확인한다. 키보드 포커스 표시를 유지한다.

### 줄 길이와 반응형 배치

- 긴 소개 문단만 `max-width: 42.5rem`(기본 환경 약 680px)을 시작점으로 삼는다. 한글 40자 안팎은 참고 목표이며 글꼴과 크기에 따라 달라진다. 실제 영역 폭은 부모 너비를 넘지 않게 한다.
- 카드·버튼·목록·전체 컨테이너에 일괄 최대 너비를 적용하지 않는다. 기존 전체 페이지 너비는 유지한다.
- 768px 전후에서 다열 카드와 상세 목록을 확인하고, 좁으면 열 수나 배치를 조정한다. 글자 크기를 줄여 해결하지 않는다.
- 주요 CTA와 모바일 메뉴 버튼은 44×44 CSS px 이상을 프로젝트 사용성 목표로 삼는다. 본문 안의 링크까지 일괄 확대하지 않는다.

## 4. 실행 순서

### 1단계: 기준 화면 보존

1. `git status`와 현재 diff를 확인하고 기존 변경·미추적 파일·stash를 보존한다. 현재 변경이 모두 이번 작업의 결과라고 가정하지 않는다.
2. `src/app/globals.css`, `src/components/Site.module.css`, `src/components/Site.tsx`, `src/components/Header.tsx`, 각 페이지와 `tests/browser-check.mjs`를 확인한다. 문구 역할 확인에는 `src/data/site.ts`를 참고한다.
3. 현재 체크아웃의 로컬 서버에서 기존 브라우저 검사를 실행하고 5개 경로 × 1440·768·360px의 기준 화면을 보관한다. 기존 서버가 오래된 빌드인지 확인하고 다른 세션의 서버는 임의로 종료하지 않는다.
4. 검사 스크립트는 `output/screenshots/{width}-{route}.png`를 덮어쓰므로 변경 전 결과를 `output/readability/before/`로 복사한 뒤 진행한다. 변경 후 결과는 `output/readability/after/`로 보관한다. 생성물은 커밋 대상에서 제외한다.

참고 사이트 추가 조사는 착수 조건이 아니다. 화면 판단이 어려운 항목만 필요한 참고 사례를 확인한다.

### 2단계: 크기·대비·배치 함께 개선

1. 공용 크기·색상 변수를 추가하고 본문·목록·안내·푸터부터 기존 선언을 수정한다.
2. 관련 미디어 쿼리와 기존 `!important` 덮어쓰기를 함께 정리한다. 같은 선택자를 파일 끝에 반복 추가하는 방식은 피한다.
3. 긴 문단 너비, 목록 간격, 카드 열 수와 긴 문자열 줄바꿈을 보완한다. 360·768·1440px 화면을 구현 중 함께 확인한다.
4. CSS로 해결할 수 없는 배치 문제에만 최소한의 마크업 수정을 한다. 사업 내용·실적 데이터와 책임 범위 안내 문구는 유지한다.

### 3단계: 검증과 결과 기록

아래 완료 조건을 확인하고 수정 파일, 검증 결과, 남은 제한을 보고한다. 단계마다 커밋이나 전체 검사를 반복할 필요는 없다. 커밋·푸시·배포는 이번 문서만으로 수행하지 않으며, 별도 요청이 있을 때 저장소 커밋 컨벤션을 따른다.

## 5. 완료 조건

- [ ] 다섯 페이지의 본문·사업 목록·공급 실적·주소가 기본 환경에서 16px 이상이고, 보조 설명은 14px 이상, 짧은 라벨은 12px 이상이다. 각 화면 폭의 최종 계산 스타일로 확인한다.
- [ ] 변경된 텍스트의 실제 전경·배경 조합이 4.5:1 이상이다. 사용한 색상 조합과 계산 결과를 남긴다.
- [ ] 1440·768·360px에서 변경 전후 15개 화면을 비교하고 겹침·잘림·의도하지 않은 가로 스크롤이 없다.
- [ ] 추가로 320 CSS px 너비에서 다섯 페이지의 가로 넘침과 긴 항목 줄바꿈을 확인한다.
- [ ] 200% 텍스트 확대 시 내용·버튼·메뉴가 잘리지 않고 사용할 수 있다. 실제 브라우저 확대 또는 동등한 텍스트 확대 조건을 사용하며, `deviceScaleFactor` 변경만으로 통과 처리하지 않는다.
- [ ] 사용자 스타일로 줄 간격 1.5배, 문단 뒤 간격 2배, 자간 0.12em, 단어 간격 0.16em을 적용했을 때 내용 손실이 없다. 언어에 적용되는 간격 속성을 기준으로 확인한다.
- [ ] 주요 CTA·모바일 메뉴의 터치 영역, 키보드 탐색과 포커스 표시가 유지된다.
- [ ] 기존 `npm test`, `npm run lint`, `npm run build`가 통과한다. 최신 빌드를 대상으로 `node tests/browser-check.mjs`를 실행한다(다른 포트는 기존 `CHECK_URL` 사용).
- [ ] 기존 모바일 메뉴, 포트폴리오 그룹·품목, 이미지, 지도·주소 링크, 404와 검색 노출 설정 검사를 통과한다. 실제 데이터 수량은 최신 코드와 기존 테스트를 기준으로 한다.

기존 브라우저 검사는 글자 대비·확대·사용자 간격까지 자동 검증하지 않는다. 이 항목은 별도 계산과 브라우저 확인이 필요하다. 임시 점검이나 기존 도구로 충분하면 새 테스트 체계를 만들지 않는다. 확인하지 못한 항목은 통과로 기록하지 않는다.

## 6. 참고 기준과 후속 결정

- [WCAG 2.2 텍스트 대비](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html): 일반 글자 4.5:1, 큰 글자 3:1. 큰 글자는 18pt(24 CSS px) 또는 굵은 14pt(약 18.67 CSS px) 이상이다. WCAG가 모든 웹 본문에 최소 16px을 요구하는 것은 아니다. 이 문서의 16px은 JNB 구현 기준이다.
- [WCAG 2.2 타깃 크기](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html): AA 기준은 원칙적으로 24×24 CSS px이며 간격·인라인 링크 등의 예외가 있다. 위의 주요 버튼 44px은 별도 프로젝트 목표다.
- [리플로우](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html), [텍스트 확대](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html), [텍스트 간격](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html)을 화면 검증 기준으로 사용한다.
- [GOV.UK 타입 스케일](https://design-system.service.gov.uk/styles/type-scale/): 기본 본문은 큰 화면·작은 화면 모두 19px, 작은 본문은 모두 16px이다. 다른 서비스의 설계 사례이며 JNB의 의무 기준은 아니다. 네이티브 앱의 pt·sp 값은 웹 px 기준으로 직접 사용하지 않는다.
- 글꼴을 통일하려면 [Pretendard 공식 배포](https://github.com/orioncactus/pretendard)의 라이선스·정적/가변·서브셋 방식을 확인하고 필요한 글리프·굵기와 실제 전송량을 측정한다. 채택 시 최종 배치 검증 전에 적용하고 `font-display`와 대체 글꼴을 점검한다. 이번에는 도입하지 않는다.
- 반복 안내는 문구별 의미와 공개 가능한 업무 범위 확인 후 정리한다. 같은 뜻의 공지만 합치고, 개별 서비스 조건·책임 범위에 필요한 안내는 관련 내용 가까이에 유지한다. 이번에는 삭제하거나 접지 않는다.

이 계획은 가독성 개선 범위의 검증 기준이며 사이트 전체의 WCAG 적합성 인증을 의미하지 않는다.
