# 확장성 개발자 독립 검토

- 검토일: 2026-10-08
- 대상: `C:/dev/JNB/JNBhomepageFront/docs/website-strategy.md` 1~170줄
- 목적: 대표님과 검토할 B2B 회사 홈페이지 초안의 준비 기준 검토. 구현·배포 승인이 아니다.
- 검토 범위: 초기 유지보수·기술·성능·변경 비용·운영 소유권. 원문만 읽었으며 다른 검토자 보고서·회사 원자료·참고 코드는 열람하지 않았다. 하위 작업자와 팀 검토를 실행하지 않았다.

**판단: 조건부 통과.** 회사 업무·경험 확인과 이메일 문의라는 목표에 비해 초기 기능 범위는 적절하다. 아래 조건을 담당자와 해결 시점을 붙여 요구사항 단계로 넘기는 전제로, 대표님 검토용 초안 준비 기준으로 사용할 수 있다. 미확인 사업 역량과 공개 사례의 타당성을 이 판단으로 승인하지 않는다.

1. **저장소 수정·재배포 방식은 유지하되 운영 담당과 반영 시간을 정해야 한다.**

   - 근거: 17줄은 관리자·문의 저장 백엔드를 제외하고, 111줄은 콘텐츠 수정 후 재배포를 정한다. 114줄은 사이트가 메일 전송 성공을 확인하지 않는다는 한계를 명시한다. 151~153줄은 재배포 운영·이메일 문의·비용을 검토 대상으로, 166줄은 운영 계정·비용 담당을 후속 확인 대상으로 둔다. 다만 실제 수정·배포·메일 응대 담당자와 기대 처리 시간은 적혀 있지 않다.
   - 추정: 수정 빈도가 낮고 개발 담당자가 계속 지원한다면 이 방식은 별도 CMS 없이도 운영 가능하다. 현재 담당자·수정 빈도·지원 지속성은 미확인이다. 트래픽보다 연락처 변경, 배포 계정 접근 상실, 문의 미응답이 초기 운영의 더 직접적인 위험일 수 있다.
   - 영향: 회사가 직접 수정할 수 없는데 개발 담당자도 없으면 오래된 사업 정보와 연락처가 남는다. 문의 저장 기능이 없는 만큼 사이트 배포 성공만으로 상담 경로의 운영 완료를 판단할 수 없다.
   - 확인 방법: 팀장이 대표님에게 콘텐츠 승인자, 수정·재배포 담당자, 필요한 반영 시간, 메일 응대 담당자를 확인한다. 공개 전에는 회사가 접근 가능한 도메인·배포 계정과 복구 수단, 결제 담당, 의존성 보안 업데이트 담당을 기록하고 대표 이메일 수신·회신을 실제 확인한다. 지금 관리자나 문의 백엔드를 추가할 필요는 없다.
   - 보완 시점: 담당자와 반영 시간은 요구사항 확정 전, 계정·복구·결제·메일 동작 확인은 공개 전.
   - 판단을 바꿀 조건: 비개발자가 자주 즉시 수정해야 하거나 담당자의 재배포 지원이 지속될 수 없다면 콘텐츠 관리 방식은 재검토한다. 공동 편집·승인 이력의 실제 필요가 생기면 CMS를, 문의 누락·담당 배정 문제가 실제로 발생하면 문의 관리 수단을 검토한다. 방문자 증가만으로 이 기능들을 추가하지 않는다.

2. **잠정 기술안은 유지할 수 있지만 참고 코드 재사용과 미디어 비용을 확정된 이점으로 보지 않아야 한다.**

   - 근거: 43~44줄의 GSPLPLUS는 기술·운영 참고다. 99줄은 흐름·공통 레이아웃 참고를, 102줄은 영상의 권리·모바일 성능 확인을 정한다. 109~117줄은 Next.js·TypeScript·CSS Modules·Vercel을 잠정 선택하고 필요한 부분만 재사용하며 정적 생성·정적 내보내기·이미지 최적화 선택과 버전 검증을 남긴다. 119줄의 플랜 조건과 153줄의 비용·용량은 확인 과제다.
   - 추정: 운영 담당자가 이 구성에 익숙하고 재사용할 코드가 작고 독립적이면 신규 기술 도입보다 변경 비용이 낮을 수 있다. 담당자 숙련도, 재사용 코드의 권리·결합도, 실제 이미지·영상 용량, 현재 호스팅 조건은 독립 확인하지 않았다. Next.js가 반드시 필요하거나 Vercel이 최저비용이라는 결론은 내릴 수 없다.
   - 영향: 참고 프로젝트 전체를 가져오면 JNB에 없는 기능과 의존성의 유지보수까지 따라올 수 있다. 정적 생성만으로 모바일에서 큰 영상·이미지의 전송 비용이나 로딩 부담이 해결되지는 않는다.
   - 확인 방법: 팀장은 구현 결정 전에 재사용 후보를 레이아웃·메뉴·메타데이터 등 필요한 부분으로 한정하고 사용 권리와 JNB 고유 정보 치환 범위를 확인한다. 대표 이미지·영상 후보의 용량, 갱신 빈도, 예상 유입을 바탕으로 최신 공식 플랜 조건·비용을 확인한다. `output: 'export'`와 이미지 처리 방식은 실제 자산과 운영 조건에 맞춰 요구사항 단계에서 결정한다. 모바일 성능 측정은 구현 후 검수에서 진행한다.
   - 보완 시점: 재사용 범위·담당자의 유지보수 가능성·비용 전제는 요구사항 확정 전, 구체적인 성능 검수 기준은 구현 착수 전, 실측은 공개 전. 이번 전략 단계에서 빌드나 속도 시험을 요구하지 않는다.
   - 판단을 바꿀 조건: 재사용 결합도가 높거나 해당 기술을 유지할 담당자가 없으면 기술안을 다시 비교한다. 실제 미디어 전송량·플랜 비용이 예산을 넘으면 먼저 이미지·영상 구성을 줄이고, 그래도 해결되지 않을 때 미디어 전달 방식이나 호스팅을 재검토한다. 측정 근거 없이 CDN·서버·데이터베이스를 추가하지 않는다.

3. **콘텐츠 조사 기록을 공개 후 갱신 책임까지 이어야 한다.**

   - 근거: 49줄은 현재 사업을 대표님에게 확인하도록 하고, 53~55줄은 대표자 경험·회사 실적·공식 관계를 구분한다. 74~77줄은 출처·날짜·수행 주체·공개 여부를 기록하고 확인된 자료만 웹 자산으로 옮기도록 한다. 93~95줄은 사례 수를 줄일 수 있고 상세 페이지도 정보가 충분할 때만 추가하도록 한다. 111줄은 저장소 데이터로 관리하지만 공개 승인자와 정보 변경 시 갱신 책임까지 정하지는 않는다.
   - 추정: 초기 사례가 소수라면 조사 목록에 승인자·승인일·갱신 책임자를 덧붙이는 정도로 관리할 수 있다. 실제 공개 가능 사례 수나 고객명·사진 사용 허가는 확인하지 않았다. GSPLPLUS 코드나 그래프는 JNB 실적의 증거로 사용할 수 없다.
   - 영향: 동일 사업·사례가 홈·사업영역·포트폴리오에서 따로 수정되면 설명이 엇갈리고, 사업 범위 변경이나 공개 철회 요청 때 누락된 내용이 남을 수 있다. 이는 페이지 수보다 콘텐츠 변경 비용과 신뢰에 직접 영향을 준다.
   - 확인 방법: 팀장은 기존 조사 목록을 재사용해 승인자·승인일·갱신 책임자를 기록하고 대표님에게 현재 사업 범위와 공개 가능한 사례를 확인받는다. 초안에서는 동일 사업명·역할·연락처의 기준 내용을 하나로 관리하도록 요구사항에 남긴다. 자료가 부족하면 사례 수를 줄이거나 명확한 검토용 자리표시자를 사용하며, 전체 회사 폴더 조사 완료를 초안 준비의 선행조건으로 만들지 않는다.
   - 보완 시점: 근거 부족 시 초안 구성 대안과 승인 책임은 요구사항 확정 전, 개별 사례·사진·고객명 공개 승인은 해당 자료 공개 전.
   - 판단을 바꿀 조건: 공개 가능한 사례를 확보할 수 없으면 포트폴리오 중심 홈 구성의 비중을 다시 검토한다. 여러 담당자가 반복 수정하거나 다국어·다수 사례에서 불일치가 실제 발생하면 콘텐츠 구조·승인 절차를 확대한다. 사례 건수만으로 CMS 도입을 결정하지 않는다.

팀장에게 위 확인 항목을 orchestration 상태 메시지로 전달했다. 실행·설치·테스트·외부 검증·전략 수정·커밋은 하지 않았으며 보고서 한 파일만 작성했다. 회사 실적과 기술·플랜 조건은 미확인 상태이므로 이를 확정 사실로 전환하거나 구현 승인으로 해석하지 않아야 한다.
